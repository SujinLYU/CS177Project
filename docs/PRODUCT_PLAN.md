# 拾拾 / Pip 产品计划

## 产品定位

**中文一句话：拾拾帮产品经理捡起会议后的小事，让注意力留给真正需要判断的大事。**

**English value proposition**

> Pip helps product managers turn meeting conversations into clear summaries and catch the small administrative tasks that are easy to miss. It prepares follow-up emails, scheduling requests, and team updates for review, then carries out approved tasks through connected tools. By reducing the mental load of remembering and coordinating these details, Pip gives PMs more room to focus on product decisions and their teams.

以上是产品愿景；当前 starter code 完成建议、编辑、审批与本地草稿生成（演示委托流程），输出可复制或下载的文本，真实第三方执行尚未接入。

核心差异不只是“更好的会议摘要”，而是发现并处理 **主要行动项周围的事务**。

| 会议内容 | 分类 | Pip 的角色 |
| --- | --- | --- |
| 决定下个版本应该解决哪个用户问题 | 产品判断 | 保留在摘要与主要行动项中，由 PM 负责 |
| 评估两个定价方案并提出建议 | 主要行动项 | 记录负责人及上下文，不当作小杂务自动执行 |
| 把评审材料发给设计同事 | 零碎事务 | 提取任务、准备草稿与材料说明，等待批准 |
| 约一个跟进时间、通知相关同事 | 零碎事务 | 整理邀请草稿，暴露缺失的时间或参与者信息 |

宠物是可亲近的入口，不是第二个待办管理系统。它应安静地提示“有几件小事待确认”，点击后进入任务列表；不随机打断，不用奖励机制催促用户。

## 首批用户与需求

**目标用户：** 每天参加多场跨职能会议、经常负责会后协调的 PM。首轮访谈可以覆盖学生项目负责人，但应分别记录他们与职业 PM 的差异。

**Job to be done：** “当我刚结束一场讨论、马上要进入下一件工作时，我想确认那些零碎的跟进事项已经被接住，并快速决定哪些可以交出去，这样就不用一直把它们记在脑子里。”

最值得验证的三个假设：

1. PM 会遗漏或延迟行政事务，并因此反复切换上下文。
2. 看到原文证据和可编辑草稿后，他们愿意批准助手代办。
3. 轻量宠物入口能帮助回到待确认任务，而不会造成新的干扰。

## MVP 形态与范围

先做 **Chrome extension + 侧边栏 + 网页内可拖动宠物**。会议记录先通过粘贴输入，减少录音、转写和会议平台集成的开发成本。Chrome 提供专门的 [Side Panel API](https://developer.chrome.com/docs/extensions/reference/api/sidePanel)，适合边看工作页面边确认任务。

网页内宠物不能跨越浏览器或悬浮在其他应用之上。若后续用户需要真正的桌面宠物，再使用 Electron 的透明、无边框、置顶窗口能力；具体平台行为见 [Electron BrowserWindow 文档](https://www.electronjs.org/docs/latest/api/browser-window)。这应是通过用户验证后的第二阶段。

**第一版用户路径：**

```text
粘贴会议记录
  → 查看摘要与主要行动项
  → 查看拾拾找到的零碎事务
  → 核对原文、负责人和待补信息
  → 编辑草稿并批准 / 忽略
  → 生成本地草稿，复制或下载
```

产品上线后的最后一步才改为调用连接工具。一次批准应对应具体任务、目标对象和最终草稿；更改这些内容后应重新确认。失败或缺失信息必须保持可见，不能显示成已完成。

| 当前 starter code | 后续开发 |
| --- | --- |
| 粘贴文本与示例会议 | 自动转写、Meet/Zoom 会议接入 |
| 演示规则分析；可选真实 AI 分析 | 提取质量评测与更完善的中文支持 |
| 摘要、主要行动项、事务列表、原文证据 | 多会议去重与跨会议上下文 |
| 草稿编辑、审批、本地草稿生成 | Gmail / Calendar / Slack 实际执行 |
| 单场会议的浏览器本地保存 | 多会议历史、账号、团队协作与受控云端同步 |
| Chrome 侧边栏与网页宠物 | 跨应用桌面宠物 |

第一版不做自主发送、不做全电脑监听、不把所有产品工作都归入“杂务”。

## 四周实施路线

| 阶段 | 工作 | 可验收结果 |
| --- | --- | --- |
| 第 1 周：问题验证与可点原型 | 访谈 5 位目标用户；用 3 段脱敏会议记录测试分类；体验当前 starter | 用户能解释它解决什么问题；列出最有价值的 2–3 类杂务与错误类型 |
| 第 2 周：真实提取 | 接入 AI 分析；用结构化输出统一数据；建立人工标注评测集；为每个任务保留证据 | 能区分主要行动项和行政事务；含糊内容显示待补充，不编造收件人或截止时间 |
| 第 3 周：单渠道闭环 | 只选 Gmail 草稿或 Calendar 邀请草稿之一；完成授权、预览、明确确认、结果记录与重试 | 能演示一项真实任务的完整闭环；重复点击不会造成重复操作 |
| 第 4 周：验证与展示 | 测量人工处理和辅助处理时间；检查宠物是否干扰；完善失败状态与演示材料 | 可复现的课堂 demo、用户反馈、指标结果和清晰的下一步决策 |

若只有两周：保留第 1、2 周与本地草稿生成，把真实第三方接入从交付范围中移除。已有原型足以验证“任务是否值得委托”和“用户是否理解审批”。

建议分工：一人负责访谈与评测，一人负责扩展交互，一人负责分析接口与执行适配。不要让前端和 AI 各自定义不同的任务结构。

## 委托模型

每项任务至少需要：类型、描述、负责人、会议原文、草稿、缺失信息和状态。原文证据能让用户判断“为什么拾拾认为我需要做这件事”。

后续真实执行的状态可以是：

```text
建议 → 待补充 / 待审核 → 已批准 → 执行中 → 已完成 / 执行失败
                    ↘ 已忽略
```

模型只提出建议；执行权限来自用户批准。执行适配器需要保存操作结果和唯一请求标识，避免网络重试重复发信。会议文本是待分析的数据，不能直接成为操作指令。

先集成 **创建草稿**，验证内容和授权体验；再把发送、发邀请等会影响他人的动作作为单独、明确的确认步骤。不要把“批准一个会议”解释成永久批准它衍生出的所有动作。

## 如何证明产品有价值

以下是首轮实验的**假设门槛**，不是已经取得的效果：

| 指标 | 测量方法 | 初步目标 |
| --- | --- | --- |
| 事务提取准确率 | 用户确认属于真实行政事务的建议数 / 全部建议数 | ≥ 80% |
| 事务提取召回率 | 已找到的真实事务数 / 人工标注的事务总数 | ≥ 70% |
| 审核成本 | 从看到建议到完成确认的实际计时 | 一段示例会议中位数 ≤ 90 秒 |
| 实际时间收益 | 对照相似任务的人工处理总时间与辅助处理总时间，包含审核、修正和重试 | 多数参与者净收益为正 |
| 信任与控制感 | 访谈中能否解释每次操作的内容、目标与批准方式 | 每位测试者都能正确解释 |
| 未经批准的外部操作 | 对照审批记录与真实执行记录 | 0 次 |

同时记录每种任务的编辑幅度、忽略原因、误判类型。不要用模型估算的“节省分钟数”替代实际计时，也不要把宠物点击数当作用户价值。

## 五个访谈 / 演示问题

1. 回想最近一次会议，你会后做了哪些没有出现在主要行动项里的小事？其中哪件最容易漏掉？
2. 这份建议列表里，哪些是杂务，哪些需要你自己判断？哪些根本不该出现？
3. 请选一个任务，边修改草稿边说出你还需要哪些信息才能放心批准。
4. 如果助手只能帮你完成一种事情，你会选什么？你希望在哪一步仍然亲自确认？
5. 请完成一个与平常相似的会后任务。宠物入口在哪些时刻帮助了你，哪些时刻让你分心？

先问真实经历，再展示产品。展示后让用户完成任务并计时，避免只收集“看起来很可爱”或“我可能会用”的评价。

## 下一步决策

先验证最有价值的任务类型，再决定集成顺序。建议默认从邮件草稿开始，因为内容容易预览、修改和对照；若访谈显示安排会议更痛，则优先日历草稿。桌面版、自动录音与更多宠物样式，都应等到核心闭环证明能减少负担之后。
